# Decisions and deviations from the plan

- mediapipe 0.10.14 and torch 2.5.1+cpu installed as planned. `kaggle` was installed, then removed (see below).
- **No Kaggle.** The team has no Kaggle account, so Phase 2 was redone with sources that need no login. Nothing is made up: every metric comes from real recordings.
- **Words: ASL Citizen instead of Kaggle ASL Signs.** Microsoft's ASL Citizen (83,399 webcam videos, 2,731 signs, 52 signers) from `https://download.microsoft.com/download/b/8/8/b88c0bae-e6c1-43e1-8726-98cf5af36ca4/ASL_Citizen.zip`. The zip supports HTTP range requests, so only the CSV splits are read up front and only the ~3,100 clips for the chosen ~100 words are streamed later. About 30 clips per sign. Splits are the official signer-disjoint ones: train 35 signers, val 6, test 11.
- Because there is no Kaggle parquet, landmarks are extracted from the video by us with the same MediaPipe `.task` models the browser uses (hand, pose lite, face), so training matches live input. Phase 3c changes accordingly: `build_words_dataset.py` streams a clip, extracts, deletes the clip.
- **License (ASL Citizen, Microsoft Research License):** non-commercial research only, no sharing or distributing the data or modifications of it, and personal data must be destroyed when the research ends. So: raw videos are never kept; `data/` stays gitignored; reference animations built from the signers' landmarks (`web/static/signs/`) are gitignored and generated locally instead of committed; trained weights and metric reports are committed (flagged as a judgement call).
- Word vocabulary is re-derived from ASL Citizen gloss names (e.g. `HELLO`, `DOG1`), one gloss per English word (the variant with most clips). The Kaggle-specific labels in the plan (`minemy`, `hesheit`, `callonphone`, ...) are dropped.
- **Letters:** `Marxulia/asl_sign_languages_alphabets_v03` (10,873 images, A to Z, no signer IDs). Its test split is NOT signer-independent and the report says so.
- **Digits:** only from ASL Citizen number signs: `ZERO`, `ONE` to `FOUR`, `SIX` to `NINE` (frames from the clips, split by signer). There is no `FIVE` sign in ASL Citizen, so **digit 5 is not supported yet** (`config.DIGITS` omits it). `Vedant3907/Numbers-Sign-Language-Dataset` was tried and dropped: its images already have MediaPipe skeletons drawn on them, so 1% of them give a detection. Adding 5 needs real samples, for example recorded in the app.
- **Emotion:** FER2013 only (`Aaryan333/fer2013_train_publicTest_privateTest`, parquet, 35k, 48x48 grey; the `Jeneral/fer-2013` copy was rejected because its `.pt` files are pickles that cannot be loaded safely). RAF-DB and AffectNet mirrors are skipped because their original licenses forbid redistribution. The plan's target of macro-F1 >= 0.70 on RAF-DB cannot be measured; the report states FER2013 test results and that FER2013 is low resolution and noisy.
- Front end: the lesson page has its own script (`lesson.js`) beside `learn.js` (course map). The dictionary's "Practise this" links to the course unit instead of opening a modal, to avoid duplicating the camera try step. The candidate confidence is a bar, not a ring.
- Landmark extraction runs MediaPipe in Python over each clip with one set of landmarkers per worker (creating them per clip leaked ~50 MB each). Two blank frames before every clip reset tracking, and timestamps keep increasing across clips. 6 workers use ~470 MB each. The zip index is parsed once in the parent and workers get byte offsets only, because parsing 83k entries per worker cost ~1 GB each.
- Hand slot assignment (nearest pose wrist, resting hands dropped) lives in `signbridge/landmarks.py::assign_hands` with a test, and `web/static/js/vision.js::assignHands` ports it. Training and the browser therefore follow one rule.
- The word model is trained on the official ASL Citizen train signers and early-stopped on the 6 validation signers. The 11 test signers are used only by `scripts/evaluate.py`.
- Landing page: grammar "live surface" (see `web/scrollcraft/builds/signbridge/BRIEF.md`, written by the team). `ffmpeg` is not installed and not needed: the page has no video. The doctor's only failed check is ffmpeg. Flask serves the build at `/` with a whitelist of files.
- Sample conversation on the landing page is scripted and says so on its face. The signing in it is the real animation data.
- **Vocabulary extended to about 280 words.** `build_words_dataset.py --append` extracts only the new words and keeps the first 100 in their original order. A hearing-to-signing synonym map in `nlg.py` (goodbye to bye, thanks to thank you, plurals and verb endings) fixes words that are in the vocabulary under another form.
- **Added:** Settings (theme, text size, reduce motion, voice, camera choice, signing defaults, data export and delete), Progress (heatmap, activity, weak spots, badges, backed by an `attempt_log` table), Phrasebook, Live Captions, Model Inspector, About, `/api/health`, locally hosted fonts, and a CI workflow (`.github/workflows/ci.yml`, not yet run on GitHub).
- `el()` now writes boolean `aria-*` and `data-*` values as "true" and "false". Before, `aria-selected` rendered as an empty string and the matching CSS never applied.
- **280-word model results** (3 seeds, 11 unseen test signers, 3,476 clips): accuracy 86.1%, macro-F1 0.862, top-3 94.7%, precision 94.0% at its acceptance threshold (coverage 83%). The 100-word core scored 89.7% on the same signers. Replaying 300 test clips through the live API gave 83.7% top-1 and an 11 ms round trip. 5,532 clips were extracted with `--append` in about 2.4 hours.
- **Extraction throughput:** 6 worker processes beat 10 (1.0 vs 0.6 clips per second). MediaPipe starts a thread pool per process, so more workers fight over the cores. `--append` takes its "already done" count from `words.npz`, not from `vocab_words.json`.
- **Landing:** the vocabulary rail (a pan act, one column per topic, 22 screens in total) and Lenis smooth scrolling for mouse and trackpad only. `/api/health` reports "degraded" if the vocabulary file and the trained model disagree.

## v2: SvelteKit front end and FastAPI backend
- **Versions (Node 20.20 and a slow registry):** SvelteKit 2.70, Svelte 5.57, Vite 6.4, Vitest 3.2, TypeScript 5.9, adapter-static 3.0. Kit 3, Vite 8, Vitest 5 and TypeScript 7 were skipped because they need Node 22 or are not supported by svelte-check yet.
- The front end is a client-only SPA (`ssr = false`, `fallback: index.html`). Its build output `web/app/build` is committed so a Python-only clone still runs.
- FastAPI keeps every API path, payload and error shape. Request models are loose (`Any`) and `services.py` keeps the original validation and messages, so errors stay `{"error": ...}` with 400, 404, 413 and 503 as before. A bad path id is 404, as in Flask.
- MediaPipe stays on the vendored 0.10.14 bundle, never the npm package, to match the training landmarks.
- Lucide and Lenis come from npm now (`@lucide/svelte`, `lenis`), so the vendored copies were removed from `fetch_assets.py`.
- The scroll-craft engine is copied unchanged to `web/app/static/landing/` and loaded only on the landing route. It has no teardown, so every link off the landing page is a full page load.
- ruff ignores E501 and B905: the code base uses dense one-liners, and the zipped sequences are equal in length by construction.
- Test tooling: `httpx` is installed for FastAPI's TestClient (a Starlette deprecation warning about `httpx2` is expected).
- Scroll-craft harness on the ported landing page: no dead scroll and all cues clear 4.5:1 at desktop, phone and reduced-motion sizes.
